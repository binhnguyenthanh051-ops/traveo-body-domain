## The design question (Wed 11 settles it in the ADR)

| | Compiler data: `-fstack-usage` + `-fcallgraph-info=su` | Disassembly: `objdump` (`push`/`vpush`/`sub sp` + `bl` edges) | Runtime high-water only (today) |
|---|---|---|---|
| Frame sizes | **Exact**, from GCC, per function (`.su`), with a static/dynamic flag | Inferred from instructions; good for leaf frames, fragile for `alloca`/VLAs | Measured, but only what actually ran |
| Call graph | GCC's own (`.ci`), incl. calls it couldn't resolve | Rebuilt from `bl`; misses tail calls (`b`) | None |
| Code it can't see | Prebuilt objects without `.su` (startup asm, any vendor binary) | Covers everything in the ELF | Covers what ran |
| Cost | A compile flag (no code change: verify the ELF is identical) | No build change at all | Free; already logged (`LOG_EVT_APP_ALIVE stack_free_words`, `g_hw_*`) |
| Worst case? | **Yes**, a static upper bound on known paths | Yes, approximately | **No**: an untaken path is invisible |

Leaning: **compiler data first, disassembly as the fallback** for objects with no `.su`, and the
runtime high-water as the cross-check (static ≥ measured must always hold, or the tool is wrong).
What every option has to state honestly, as annotations in a small data file:
- **indirect calls**: function pointers, e.g. the IPC port and crypto transport
- **recursion**, if any
- **ISRs/exception frames**: up to 104 B with FPU lazy stacking on the M4F/M7, added on top
- **library calls** without data: newlib, PDL
