## Process findings: why the traceability gaps got this far

The W42 retro audit and the first `trace_report.py` run (2026-10-19) found test-traceability gaps
in a milestone that had already been tagged `m5-secoc`: REQ-SECOC-011 had no `@test` or
`@design-only` tag, and the coverage matrix claimed tests that carry no tag for the REQ
(REQ-SECOC-002 → `test_crypto_mac`, REQ-SECOC-007 → `test_secoc`). The findings below are the
root causes of that. They are about how the work was done, not about the code.

### M5-R1: "done" did not include traceability when M5 was built
**Status:** closed (2026-10-18)

When M5 was built and tagged, the Definition of Done was tests passing, a working bench and a
published post. Traceability (requirement → ADR → `@impl` → `@test` → silicon evidence) wasn't
part of it, so no step made anyone go back to the coverage matrix once the tests were green. The
matrix was written from the design in the same commit as the tests (`16a4770`), and nothing
checked one against the other afterwards.

**Closed by:** rule 11 in `docs/project/plan.md` (W42 retro): traceability and a generated
report are DoD checks 1–6. The report tool exists from 2026-10-19 and exits 1 on gaps.
**Still open from this:** wiring `trace_report.py --check` into CI once the baseline gaps are
triaged (Sun 25). Until then rule 11 is enforced by hand.

### M5-R2: nobody checked that each `@test` tag proves its REQ
**Status:** open, closed by this record's test section (Thu 22)

Per `docs/workflow.md`, Copilot writes the Unity test cases, and the `@test` tags were added
along with them. A tag on a passing test *looks* like coverage, but the tag only says what the
test is meant to verify. Nobody asked whether the test really checks what the REQ says, fail
paths included. Claude Code reviewed the code before commit but didn't treat the tags as claims
to verify. A script can't answer this either: `trace_report.py` checks that tags exist and
match the matrix, not that they're true.

**Closed by:** the test section below, which goes through every `@test` in
`docs/traceability.md`. From M5B on, a test tag counts as reviewed only once that section has
looked at it.

### M5-R3: the request was not clear, so the owner and the AI tools understood "traceability" differently
**Status:** open, closed by an explicit acceptance criterion in future requests

The owner's request when M5 was built didn't say clearly that traceability meant *verified*
links: each tag checked against the REQ's wording and the matrix kept in sync with the tags.
That left a gap between the owner's understanding and the tools'. To Claude Code and Copilot,
"add traceability" meant "put a tag on the code and the test". To the owner it meant "show that
each requirement is really proven". Neither side named the difference. Claude Code didn't ask,
although CLAUDE.md tells it to challenge unclear decisions, and the request didn't say what
done looked like.

**Action:** requests for code that serves a `REQ-*` state the acceptance criterion explicitly,
for example: "tags present, each `@test` checked against the REQ including fail paths, matrix
matches, `trace_report.py` has no new gaps". Claude Code asks when the criterion is missing
instead of assuming one. Closed when this is written into `docs/workflow.md` (Claude Code ↔
Copilot handoff rule).
